# Bite data model

Source of truth is `packages/db/src/schema`. This doc explains the why.
Agreed with Nasser on 2026-11-17.

## Ground rules

| Rule                                                                    | How it is enforced                                                                     |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Ids are UUIDv7, generated by whoever creates the row (tablets included) | `id()` helper; clients may send their own                                              |
| Money is int8 minor units (baisa), never decimal/float                  | `money()` helper, `@bite/core` math                                                    |
| Rates are integer basis points (5% = 500)                               | `*_bps` columns                                                                        |
| Every tenant row carries `org_id`                                       | `orgId()` helper                                                                       |
| A tenant can only see its own rows                                      | RLS policy `org_id = app_org_id()` on all 24 tenant tables                             |
| A row can only point at rows of the same tenant                         | Composite FKs `(org_id, x_id) → (org_id, id)`. RLS does not cover FK checks, this does |
| A forgotten tenant context returns nothing                              | `app_org_id()` is NULL when unset, and NULL never matches                              |
| Migrated legacy rows are traceable                                      | `legacy_id` on migrated tables                                                         |

## Tenancy and access

```
orgs ─┬─ locations ─── devices (tablets, revocable token, ticket prefix)
      ├─ members ───── member_locations (role per location)
      └─ billing_subscriptions
```

- **orgs** is the customer account. **locations** is a branch. RLS is keyed on the org; the location is a normal filter.
- **members** covers everyone in an org. `user_id` links to a Better Auth login (owners, admins, managers). Floor staff usually only have a `pin_hash`. Their role is per location (`manager`, `cashier`, `server`, `kitchen`).
- **billing_subscriptions** and the org's `status`, `trial_ends_at` and `entitlement_overrides` decide the org's plan. The app role can read them but not write them. See `docs/plans.md`.
- **devices**: each tablet has a `ticket_prefix` (A, B, …) that is unique per location, so offline tickets never clash (`A-042`).
- Location settings that used to live in the `branding` blob are now typed columns: timezone, currency, `prices_include_tax`, `tax_bps`, VAT number, `day_cutoff_minutes`, contact. Only the visual theme stays jsonb.

## Menu

- The menu belongs to the **org**. `product_location_settings` overrides price and availability (86'd) per location. **My call, not discussed yet.** The alternative is a menu per location, which is simpler for a single shop but means duplicating everything for branch #2.
- Localized text is jsonb `{ en, ar? }`.
- `products.price` is gross or net depending on the location's `prices_include_tax`.
- Products are archived (`archived_at`), never deleted, because order lines point at them.
- **promotions** replaces both product discounts and `pricing_rules`. The target is a product, a category or the whole menu. The window is an optional date range + optional daily time window (can wrap midnight) + optional weekdays. Several can match one line: **highest `priority` wins, no stacking.** That is also my call.

## Orders

- `payment_status` (unpaid → partially_paid → paid → partially_refunded/refunded) and `fulfillment_status` (pending → preparing → ready → completed, or cancelled) are separate. The transitions live in the `@bite/core` state machine, not in the DB.
- `ticket_number` is unique per location per `business_date`. Tablets use `<prefix>-<seq>`; guest/QR orders get a server-allocated `Q-<seq>`.
- `business_date` is the local day after the cutoff, so a 1 AM sale counts toward the previous day.
- Totals (`subtotal`, `discount_total`, `tax_total`, `total`) are computed by core pricing and stored. `prices_include_tax` is snapshotted on the order.
- `paid_total` is denormalized and must be updated in the same transaction as payment inserts.
- `version` is bumped on every write; the sync protocol uses it to detect conflicts.
- Idempotency: unique `(org_id, idempotency_key)` + fingerprint, same as legacy.
- **order_lines** snapshot the name, list price, promoted unit price, promotion, modifiers (jsonb), tax rate and line tax/total. Lines are voided, never deleted.
- **order_feedback** has moved out of the orders table.

## Money

- **payments** is an append-only ledger. A split bill is several positive rows. A refund is a new negative row with `reverses_payment_id`. The DB enforces: amount ≠ 0, negative ⇔ reverses something, cash ⇒ has a cash session, `tendered` only for cash.
- Async providers (Thawani, terminal) insert `pending` and move to `succeeded`/`failed` once; that is the only update allowed.
- `(provider, provider_reference)` is unique, so a webhook can't double-book.
- **cash_sessions**: one open session per device (partial unique index). It opens with a float and closes with a count; `expected_cash`, `counted_cash` and the denomination breakdown are stored at close.
- **cash_movements**: pay-in, pay-out and drop, always positive, with a mandatory reason.

## Sync

- **sync_mutations** is the idempotency ledger for offline outbox replay, keyed `(org_id, id)` where `id` is the client mutation id. A row is written in the same transaction as the mutation's effect, and only for final outcomes (applied or rejected), so replay returns the original result. Conflicts and "blocked" are not recorded. They're retryable. `fingerprint` (sha256 of the canonical mutation) catches an id reused for a different body. The ledger is append-only for the app.
- **orders.change_xid** (`xid8`) is set to the writing transaction's id by a trigger on every update. Sync pull hands out the snapshot `xmin` as its cursor and returns rows with `change_xid >= cursor`. A transaction that was still in flight during a pull has an xid at or above that xmin, so its rows come back on the next pull. Rows can repeat, and clients upsert by `version`. Payments and voids always update their order row, so they move the cursor too.

## Group carts

The legacy JSON blob is replaced by real rows:

- **group_carts**: `open → locked → submitted` (or expired/cancelled). `version` gives optimistic concurrency. Submitted ⇔ `order_id` set, and one cart makes at most one order.
- **group_cart_participants**: each guest has a secret hash kept in their browser, so they can only edit their own items. Exactly one host.
- **group_cart_items**: ids only, **no prices**. The cart is always re-priced from the live menu at submit, so a tampered or stale cart can't set prices.

## Loyalty

**customers** are per org (shared across branches) and unique by E.164 phone.

## System

- **audit_log** is append-only for the app: no update/delete policy, and the privileges are revoked.
- **webhook_events** is cross-tenant, so it has no RLS and only `bite_system` can touch it.

## Roles

| Role               | Used by                                   | RLS                                                    |
| ------------------ | ----------------------------------------- | ------------------------------------------------------ |
| owner (migrations) | `drizzle-kit` / deploy                    | bypasses as owner, never used by the app               |
| `bite_app`         | API, per-tenant workers                   | enforced; tenant set per transaction by `withTenant()` |
| `bite_system`      | provisioning, webhooks, cross-tenant jobs | BYPASSRLS, keep its use tiny                           |

### Pre-tenant lookups

Some requests must find their tenant before one is set: a device token, a guest menu slug, a guest tracking link, a group cart share link. `bite_app` can't see those rows without a tenant, so `SECURITY DEFINER` functions do exact-match lookups and return only ids: `auth_device(token_hash)`, `resolve_location_slug(slug)`, `resolve_tracking_token(uuid)`, `resolve_group_cart_token(uuid)` (migration 0004), and `user_memberships(user_id)` (0011, back-office login to its active memberships), `resolve_invite(token_hash)` (0013, open staff invite). Revoked devices, inactive locations and suspended orgs resolve to nothing. They are `EXECUTE`-only to `bite_app`, and the caller then opens `withTenant()` with the returned org. Don't add a definer function that returns rows or takes a pattern.

### Back-office logins (Better Auth)

`auth_users`, `auth_sessions`, `auth_accounts`, `auth_verifications` hold identities only and have **no RLS**: one login can belong to several orgs, and the session is read before any tenant is known. Nothing tenant-shaped goes in them. `members.user_id` points at `auth_users.id` (set null on delete). What a login may do is decided by its `members` row, read under RLS after `user_memberships()` picks the org. A test pins the full list of tables without RLS (the four above plus `webhook_events`), so adding another one is a deliberate act.

Onboarding needs no definer function: the API mints the new org id, opens `withTenant(newId)` and inserts the org, location and owner. The `own_org_insert` policy only allows inserting the org whose id is the current tenant.

`webhook_events` is system-only. Migration 0011 revokes the blanket default grant from `bite_app`.

Roles are created once per cluster by `packages/db/sql/bootstrap-roles.sql`. `withTenant()` uses `set_config(..., true)` (transaction-local), so it is safe behind a transaction-mode pooler.
